Brokerage data for grounded AI answers

At Appmosis, I owned the launch of a feature that answers questions using a user’s actual portfolio holdings. Appmosis is a San Francisco fintech startup with 15–30 people and fewer than 1,000 users at the time described.

6–8 weeks From specification to general availability, in partnership with engineering.
Brokerage APIs → Common data model → Relevant holdings → Grounded answer

Problem

Brokerage APIs describe positions differently. Inconsistent inputs could corrupt portfolio reporting and give an AI feature unreliable context.

Decision

Normalize each broker’s JSON into a common schema and upsert positions in GCP Spanner by account and symbol. At question time, query only the relevant holdings and format a compact context block. The answer uses portfolio state as of the last sync.

Implementation & ownership

I owned the launch from specification to release: defined context-window injection logic and prompt architecture, and coordinated engineering delivery. I built Python transformations for 5+ brokerage APIs, used SQL for launch measurement, and built dashboard validation checks.

Outcome

The feature reached general availability. My validation investigation traced incorrect portfolio totals to null prices on halted stocks and resolved the issue before release. I also measured initial key connections after launch; the historical active-user cohort count is not available for this case study.

Inspect the normalization example

This new, independent example uses invented broker payloads. It demonstrates the transformer pattern and preserves a missing price as unknown; it contains no employer code or data.

python brokerage_normalization/normalize.py
python -m unittest discover -s tests -v

The output distinguishes known market value from completeness. A halted position remains incomplete instead of silently receiving a zero price.
